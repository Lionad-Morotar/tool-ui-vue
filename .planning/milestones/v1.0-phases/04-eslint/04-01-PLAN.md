# Phase 4: Quality + Compat — i18n CI 门禁与向后兼容保障

## Goal

为 i18n 系统建立 CI 门禁和向后兼容保障。覆盖：消息 Key 一致性校验（QUALITY-01）、新增组件硬编码英文检测（QUALITY-02）、无 LocaleProvider 时组件默认行为（COMPAT-01）、copy-paste 消费者零侵入（COMPAT-02）。

## Current State

- 25 个组件已接入 `useI18n()`；3 个组件（image-gallery, link-preview, progress-tracker）未接入
- `useI18n()` 无 LocaleProvider 时 fallback 返回 **key 字符串**，不是 zh-CN 消息文案
- CI 只有 `deploy-histoire.yml`，无质量门禁
- ESLint 已有自定义插件模式（`lib/*.mjs`），flat config（`eslint.config.mjs`）

## Success Criteria

1. zh-CN 和 en 消息文件 key 树不一致时 CI 失败
2. 新增组件未使用 `t()` 包裹 UI 文本时 CI 脚本告警
3. 无 LocaleProvider 时组件以 zh-CN 默认消息正常渲染（不显示 key 字符串）
4. copy-paste 消费者（无 `@lionad/core` 依赖）使用组件与之前完全一致

## Plan

### Task 1: 修复 useI18n() 无 LocaleProvider 时 fallback 为 zh-CN 消息

**问题**：当前 `useI18n()` 在没有 LocaleProvider 和全局 messages 时，`t()` 返回 key 字符串（如 `"terminal.copy"`），不是用户可读的文案。

**修改**：`packages/core/src/i18n/use-i18n.ts`

```typescript
// 新增：导入内置 zh-CN 默认消息
import { zhCN } from './locales/zh-CN'

// 当无 context 且无全局 messages 时，使用 zhCN 作为兜底
const t = <TKey extends string>(key: TKey, params?: Record<string, ParamValue>): ComputedRef<string> => {
  return computed(() => {
    const resolved = resolveMessage(zhCN, key) ?? key  // 从 zhCN 解析，而非直接返回 key
    return interpolate(resolved, params)
  })
}

// dev 模式 warn 开发者建议配置 LocaleProvider
if ((import.meta as any).env?.DEV) {
  console.warn(`[vtu:i18n] No LocaleProvider configured. Using built-in zh-CN messages as fallback.`)
}
```

**console-guard 更新**：在测试 setup 中添加 `[vtu:i18n] No LocaleProvider` 到 ALLOWED_PATTERNS。

### Task 2: 为 useI18n fallback 添加测试（含现有测试修复）

**文件**：`packages/core/src/i18n/__tests__/use-i18n.test.ts`

**现有测试冲突**：
- 第 122-127 行已有测试 `'t() returns key itself when messages not set'` 断言 `t('any.key')` 返回 `'any.key'`
- `beforeEach` 调用 `setMessages({})`（空对象 truthy），导致 `!_messages.value` 为 false
- Task 1 修改后 fallback 行为变为返回 zh-CN 文案

**修复策略**：
1. 更新现有 fallback 测试：`setMessages(null)` 清除全局 messages，验证 `t('shared.copy')` 返回 `'复制'`（zh-CN 内置值）
2. 添加新测试：`setMessages(null)` 后调用 `t('nonexistent.key')`，验证不存在 key 仍返回 key 本身
3. 添加新测试：验证 dev 模式下 console.warn 出现（允许模式过滤后通过）
4. 其余测试保持 `setMessages({})` 不变 — 它们测试的是 LocaleProvider 模式，不受影响

```typescript
test('falls back to zh-CN messages when no provider and no global messages', () => {
  setMessages(null)
  const { t } = useI18n()
  expect(t('shared.copy').value).toBe('复制')
})

test('falls back to key when key not in zh-CN messages', () => {
  setMessages(null)
  const { t } = useI18n()
  expect(t('nonexistent.key').value).toBe('nonexistent.key')
})
```

### Task 3: 创建 i18n 校验脚本

**文件**：`scripts/check-i18n.mjs`

**功能**：
1. **key 一致性校验**（QUALITY-01）：读取 `zh-CN.ts` 和 `en.ts`，对比顶层 key（命名空间级别），发现缺失或多余的 key 时报 error
2. **组件 i18n 覆盖检查**（QUALITY-02）：扫描 `packages/components/src/*/` 下每个组件目录：
   - 组件 `.vue` 文件是否包含 `useI18n` import
   - 如果不包含，检查是否已知白名单（image-gallery, link-preview, progress-tracker）
   - 白名单外未使用 i18n 的组件 → exit 1
   - 对已使用 `useI18n` 的组件，检查模板中是否仍然有未使用 `t()` 的常见 UI 英文（简单启发式：检测 `>{{` 后的英文单词，排除 `class`/`style`/`data-*` 属性值）

**输出**：
```
✅ Key consistency: zh-CN (23 namespaces) ↔ en (23 namespaces)
✅ i18n coverage: 25/25 components use useI18n()
✅ 3 layout-only components whitelisted: image-gallery, link-preview, progress-tracker
```

**退出码**：key 不一致 → exit 1；未白名单组件缺少 i18n → exit 1

### Task 4: 添加 ESLint i18n 插件

**文件**：`lib/eslint-plugin-i18n.mjs`

参考现有 `lib/eslint-plugin-v-tw-merge.mjs` 模式，创建包含 `key-consistency` 规则的 ESLint 插件：

```javascript
// lib/eslint-plugin-i18n.mjs
const keyConsistencyRule = {
  meta: { type: 'problem', docs: { description: 'zh-CN and en locale key trees must match' } },
  create(context) {
    // 对比两个 locale 文件的 key，不一致时报 error
  }
}
export default { rules: { 'key-consistency': keyConsistencyRule } }
```

**注册到** `eslint.config.mjs`：
```javascript
import i18nPlugin from './lib/eslint-plugin-i18n.mjs'
// plugins 中添加 'i18n': i18nPlugin
// rules 中添加 'i18n/key-consistency': 'error'
```

**注意**：`no-hardcoded-strings` 规则推迟实现。其检查职责由 Task 3 的脚本承担（脚本方案误报率更低，因为可以手动维护白名单）。

### Task 6: COMPAT-02 copy-paste 消费者验证

**背景**：copy-paste 消费者（直接复制 `.vue` 文件到项目，不依赖 `@lionad/core`）目前无法单独使用组件，因为组件内 `import { useI18n } from '@lionad/vtu-core/i18n'` 会报错。这是 Phase 1 以来的既有行为，Phase 4 不改变此状态。

**验证**：在 `04-CONTEXT.md` 中记录此限制为已知行为。Phase 4 通过 Task 1 的 fallback 机制确保：如果消费者同时也复制了 core/i18n 模块（不使用 LocaleProvider），组件仍能正常渲染 zh-CN 文案。

**具体行动**：在 `packages/core/src/i18n/__tests__/locale-provider.test.ts` 中添加测试，验证：不通过 provide 注入 messages 时，组件仍能渲染 zh-CN 文本（证明 copy-paste + core i18n import 但不配置 LocaleProvider 的场景可行）。

## Risks

- **ESLint 规则误报**：`key-consistency` 只对比顶层 key 树，不会深入到嵌套 key，避免误报
- **fallback 消息体积**：zh-CN 消息文件约 10-20KB，导入 core bundle 影响可忽略（tree-shaking 后更小）
- **console-guard 影响**：需要为 fallback warning 添加 ALLOWED_PATTERN
- **`setMessages({})` vs `setMessages(null)`**：测试中必须明确区分 — 空对象 `{}` 是 truthy，不会触发 fallback；`null` 才会
